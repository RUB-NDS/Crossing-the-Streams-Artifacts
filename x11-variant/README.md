# x11-fwd: server→client X11 cookie exfiltration PoC

Standalone proof-of-concept demonstrating that an unprivileged co-tenant on
a multi-user OpenSSH server may be able to recover the per-session X11 fake
proxy cookie generated by `ssh -X` and use it to authenticate against the
victim's forwarded X server — by injecting chosen plaintext through the X11
forward TCP socket and observing compressed-byte deltas.

See `../docs/superpowers/specs/2026-04-29-x11-fwd-design.md` for the full
design and `../docs/superpowers/plans/2026-04-29-x11-fwd.md` for the 15-task
implementation plan that built this PoC.

## Threat model summary

- Attacker is a separate Unix user on the SSH server. No `CAP_NET_RAW`,
  no sudo, no membership in the victim's groups; the victim's home is mode
  0700 to keep the attacker out.
- Attacker can: read `/sys/class/net/eth0/statistics/tx_bytes` (world-
  readable), open TCP connections to localhost ports.
- Attacker target: the 16-byte fake cookie generated by OpenSSH's
  `x11_request_forwarding_with_spoofing` per session.

## Topology

- **`client` container** — the victim's workstation. Runs Xvfb (with the
  SECURITY extension explicitly enabled) and a harness HTTP service at
  port 8000. The "victim" user runs an interactive
  `ssh -X -T victim@server bash` session driven by the harness.
- **`server` container** — the multi-user host. Runs sshd (cipher pinned to
  `chacha20-poly1305@openssh.com`, X11 forwarding on) and the attack engine
  HTTP service at port 9000 as the unprivileged `attacker` user.

The two containers share a private bridge network and a `/srv/keys` volume
that hands the victim's ed25519 key from the server image (where it's
generated at build time) to the client.

## Run a trial

```bash
cd x11-variant
python3 scripts/run_trial.py
```

A successful run prints `OVERALL: PASS` and exits 0. **See "Validation
status" below — full end-to-end recovery has not yet succeeded in this
build.**

## Pure-logic tests (no docker, no SSH)

```bash
cd x11-variant && PYTHONPATH=server python3 -m unittest discover -s tests -v
```

26 tests covering the probe layout, sysfs counter reader, engine ranking,
recovery loop, and X11 connection-setup builder — all pass.

## Tuning knobs (engine, via env on the `server` service)

- `SETTLE_S` (default `0.15`) — sleep after probe TX before reading
  `tx_bytes`. Widen if `tx_bytes` undercounts on slow stacks.
- `COOKIE_LENGTH` (default `16`) — number of bytes to recover. Set to a
  small number for shorter smoke tests.
- `MAX_ROUNDS` (default `16`) — per-position round budget before
  `RecoveryFailed` is raised.
- `MIN_MARGIN` (default `8`) — required byte gap between top candidate's
  median and runner-up's median for a position to lock.
- `MIN_AGREEMENT` (default `5`) — required number of alignment offsets
  (out of 8) on which the top candidate must win.
- `TX_BYTES_PATH` (default `/sys/class/net/eth0/statistics/tx_bytes`) —
  override if eth0 is not the egress interface.

The engine logs per-round per-byte progress at INFO level
(`byte=N round=R top=0xXX med=N runner=0xYY med=M margin=K agree=A/8`),
which makes it possible to diagnose whether convergence is stalled or
the signal is below the noise floor.

## Validation status

**Infrastructure: complete and verified.**
- 26 pure-logic unit tests pass.
- `ssh -X` login + X11 forwarding round-trips `xset q` end to end.
- Negotiated cipher pinned to `chacha20-poly1305@openssh.com`.
- Harness drives an interactive `ssh -X -T … bash` subprocess with
  sentinel-token sync.
- Engine HTTP service `/run_attack` reaches the oracle, builds probes via
  `inject.build_probe`, and reads `tx_bytes` deltas.
- `/e2e_check` builds a valid X11 connection-setup (verified by unit
  tests against byte-exact layout).

**Cookie recovery: not yet succeeding** (one passing trial, the spec's
definition of done, has not been demonstrated). End-to-end runs surface
two issues the original design did not anticipate:

1. **`tx_bytes`-granularity signal is too coarse for single-byte
   compression deltas at this probe size.** The total egress per
   measurement is dominated by ~400 bytes of fixed SSH/TCP framing
   overhead (3 SSH packets × {16-byte ChaCha20-Poly1305 MAC, 8-byte
   alignment padding, ~20 bytes of TCP/IP header} per packet). A
   single-byte CRIME-style match savings (~1 byte uncompressed,
   typically <8 bytes encrypted after alignment) is below the noise
   floor.
2. **The X11-forward channel only fully transmits the *first* probe
   per SSH session.** The SSH client's `x11_open_helper` rejects each
   bad-cookie connection-setup, and after the first rejection,
   subsequent x11 channels appear to forward only ~80 bytes of payload
   regardless of probe size. A 10 KiB random probe shows in `tx_bytes`
   only on the first measurement; subsequent measurements drop to
   ~400-490 bytes.

A direct compression diagnostic (probing with the *known-correct* full
16-byte cookie vs. all-zero bytes after the anchor) shows no
distinguishable size delta in the steady state — confirming the issue is
not in the engine's ranking algorithm but in the measurement /
forwarding pipeline.

## Out of scope (per spec, also not addressed by this build)

- Multi-trial benchmarking and statistical accuracy across many cookies.
- Attacking AES-GCM or AES-CTR ciphers (different alignment granularity).
- Attacking `-Y` trusted forwarding (mechanics are identical, but the
  spec pins `-X` for clarity of the threat-model story).
- Recovery of the user's real `~/.Xauthority` cookie. The fake cookie
  is what authenticates against the SSH-forwarded X server, which is
  the attack's value proposition under this threat model.

## What would unblock end-to-end recovery (not implemented)

The two issues above suggest at least these directions for future work:

- **Finer-grained measurement.** Replace `tx_bytes` polling with
  per-packet inspection (`tcpdump`/scapy with `CAP_NET_RAW`) to expose
  the size of *just* the SSH `CHANNEL_DATA` packet carrying the probe,
  rather than the union of all server→client traffic during the settle
  window. This breaks the attacker model (a co-tenant doesn't have
  `CAP_NET_RAW` by default), but would prove the algorithm works.
- **Larger compression delta per probe.** Make the candidate appear in
  multiple back-reference contexts (e.g., probe = anchor + candidate +
  filler + anchor + candidate, or longer matches that span more
  alignment slots). A multi-byte savings differential would survive
  alignment quantization.
- **Keep the X11 channel forwarding alive across probes.** Construct
  probes that look like valid X11 protocol after the connection-setup
  (e.g., send the cookie exactly once at the start of each TCP
  connection, then prepend `<short_bigreq><probe>` so the channel
  doesn't auth-fail). This requires sending a known-valid cookie up
  front, which contradicts the threat model (we don't know it yet),
  unless we phase the recovery: first byte via "known-valid" cookie
  candidates, etc.
